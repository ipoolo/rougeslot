# 双峰多巴胺体验模型 · 公式规范

> 版本：`202607-draft.3`
> 状态：公式主干与一级分类已确认，部分细分边界待后续案例校准  
> 适用范围：202607 新版网页第一部分，以及所有机制母型、品类原型、游戏变体的共同公式底座

---

## 1. 模型定位

### 1.1 体验目标

```text
持续爱干
```

这里的“持续爱干”指玩家在多次短循环之后，仍愿意主动开始下一次操作、继续观察结果并调整构筑。

### 1.2 体验模型

```text
双峰多巴胺
```

双峰多巴胺是本项目用于组织游戏体验与机制设计的**体验设计模型**：

- 第一峰来自 `Random + Put`。
- 第二峰来自 `Combo`。
- `BD` 把一次次结果转化成后续调整，让两个峰值持续循环。
- 可选的 `P(t)` 以目标、期限、当前差距与失败代价包裹完整循环，使每次结果具有“够不够”的意义。

本模型本质上是对这类游戏的抽象假设。

## 2. 核心公式

### 2.1 主公式

```text
P(t) ⟦
  [
    Random @ Pool_Symbol
      →
    Put @ Show_TP
      →
    Combo(C₁ → C₂) @ Show_TP
  ]ₙ
    →
  BD
⟧
```

紧凑写法：

```text
P(t) ⟦ [ Random@Pool_Symbol → Put@Show_TP → Combo(C₁→C₂)@Show_TP ]ₙ → BD ⟧
```

其中核心运算公式仍是：

```text
[ Random@Pool_Symbol → Put@Show_TP → Combo(C₁→C₂)@Show_TP ]ₙ → BD
```

`P(t)` 是可选的**目标压力域**，`⟦ ⟧` 表示它包裹完整循环。它不是乘法，也不是第五个操作步骤。

### 2.2 P(t) 的外层边界

`P(t)` 至少可以包含：

- 当前目标或达标阈值。
- 距离目标的当前差距。
- 剩余时间、Spin、回合或关卡。
- 未达标的失败代价。
- 随进度增长、收紧或变化的压力曲线。

已确认边界：

1. `P(t)` 为每次 `Spin_Result` 提供“是否足够”的价值判断，并影响玩家的 BD 方向。
2. `P(t)` 不直接参与符号抽取、放置或协同计算。
3. `P(t)` 的目标检查周期与 `N` 分开记录。
4. 没有硬性失败压力的游戏，可以采用软目标或令 `P(t)` 不适用。

以《幸运房东》为例：

```text
P(t) = 当前房租 + 剩余 Spin + 当前金币缺口 + 未达标后果
```

每次 Spin 后选择新符号属于 `N = 1 → BD`；若干次 Spin 后的房租检查属于 `P(t)` 的更长目标周期。两者不能合并成同一个 N。

### 2.3 已确认的三个作用域边界

1. `Random` 只直接作用于 `Pool_Symbol`。
2. `Put` 发生在 `Show_TP` 上。
3. `Combo` 与 Put 共用同一个 `Show_TP`。

### 2.4 `@` 的含义

`@` 是**作用域／承载域标记**，不是乘法。

```text
Random @ Pool_Symbol
```

表示 Random 从 `Pool_Symbol` 中进行本次随机选择。

```text
Put @ Show_TP
```

表示 Put 把本次抽取结果写入或安置到 `Show_TP`。

```text
Combo(C₁→C₂) @ Show_TP
```

表示 Combo 在同一个 `Show_TP` 及其当前状态上完成判定和结算。

## 3. 单次 Spin 数据流

```text
P(t)
Pool_Symbol
  ── Random ──>
SingleSpin_Symbol
  ── Put @ Show_TP ──>
Show_State
  ── Combo(C₁→C₂) @ Show_TP ──>
Spin_Result
```

### 3.1 输入与输出

| 阶段 | 输入 | 操作 | 输出 |
|---|---|---|---|
| P(t) | 目标、期限、进度差距、失败代价 | 包裹并评价完整循环 | 结果价值判断与构筑方向 |
| Random | `Pool_Symbol` | 从符号池中完成本次随机选择 | `SingleSpin_Symbol` |
| Put | `SingleSpin_Symbol` + `Show_TP` | 把本次结果安置到承载空间 | `Show_State` |
| Combo | `Show_State` + `C₁` + `C₂` | 在承载空间中判定并结算 | `Spin_Result` |
| BD | 一段周期内的结果和当前构筑状态 | 玩家进行构筑决策 | 后续循环的参数变化 |

### 3.2 Show_TP 与 Show_State

```text
Show_TP    = 空间类型
Show_State = 某次 Spin 中这个空间的具体状态
```

例：

```text
Show_TP    = 2D Grid
Show_State = 本次 Spin 得到的实际符号排列
```

因此：

- Put 写入 `Show_TP`，形成 `Show_State`。
- Combo 读取 `Show_State`，但判定关系受 `Show_TP` 的空间结构约束。

### 3.3 Pool_Symbol 详解

`Pool_Symbol` 是 Random 唯一直接读取的内容域，它回答：

> 一次 Random 有可能从哪些符号中进行选择？

Pool_Symbol 至少需要描述：

- 符号的身份与类型。
- 符号在池中的数量或权重。
- 符号是否允许重复出现。
- 当前哪些符号可被 Random 读取。
- BD 是否能够增加、删除、替换或调整符号。

Pool_Symbol 不等于本次抽取结果：

```text
Pool_Symbol       = 可被选择的总体内容
SingleSpin_Symbol = 某次 Random 实际选择出的内容
```

Pool_Symbol 也不直接规定：

- 抽取结果怎样排列。
- 抽取结果进入哪种空间。
- 符号之间怎样协同。

这些分别由 Random 参数、Put、Show_TP 和 Combo 继续规定。

机制母型可以为 Pool_Symbol 提供先验结构；品类原型和游戏变体则继续限制符号内容、权重和 BD 的修改方式。

### 3.4 Show_TP 详解

`Show_TP` 是 Put 与 Combo 共同使用的空间结构类型，它回答：

> 本次抽取结果在什么结构中被呈现、被放置，并被 Combo 判定？

Show_TP 已确认沿用五类：

| key | 中文名 | 核心结构 | 可产生的典型关系 |
|---|---|---|---|
| `0D_multiset` | 0D 多重集 | 无位置、无顺序，只保留类型和数量 | 数量、重复、类型组合 |
| `1D_sequence` | 1D 序列 | 元素具有前后次序，两端不相接 | 先后、连续段、前后影响 |
| `1D_ring` | 1D 圆环 | 一维次序首尾相接 | 环上邻接、循环距离、落点 |
| `2D_grid` | 2D 离散网格 | 元素位于离散的行列坐标 | 上下左右、对角、连线、区域 |
| `2D_physical` | 2D 连续物理空间 | 元素具有连续坐标和物理过程 | 路径、距离、碰撞、反弹 |

Show_TP 与 `SingleSpin_Symbol` 的结构不能强制等同：

- SingleSpin_Symbol 不严格定义为无序多重集。
- Random 的输出在某些机制中可能具有自身结构。
- Put 仍负责把本次结果写入最终用于呈现和 Combo 判定的 Show_TP。

一个具体机制可以继续规定：

- 采用哪一种 Show_TP。
- Show_TP 的尺寸和边界。
- Put 可以修改哪些位置。
- Combo 可以读取哪些空间关系。

## 4. 三个阶段的职责边界

## 4.1 Random

工作定义：

> Random 是从 `Pool_Symbol` 的内容中，为一次 Spin 随机选择出 `SingleSpin_Symbol` 的过程。

Random 负责：

- 从什么池中抽取。
- 一次抽取多少内容。
- 各内容被选中的概率。
- 是否放回、是否加权等随机规则。

Random 不负责：

- 把结果放到哪个位置。
- 玩家如何调整位置。
- 结果之间如何协同。
- 最终如何结算。

这些分别属于 Put 与 Combo。

`SingleSpin_Symbol` **不严格定义为无序多重集**。

正式定义：

> SingleSpin_Symbol 是尚未经过 Put 写入 Show_TP 的本次抽取结果。它可以是单个符号、一组无序符号，也可以在具体机制中具有其他结构；是否有序、是否允许重复，由机制母型和下层原型规定。

它与 Show_TP 的关键区别是：SingleSpin_Symbol 描述 Random 输出了什么，Show_TP 描述这些内容最终在哪种结构中被 Put 与 Combo 使用。

## 4.2 Put

工作定义：

> Put 是把 `SingleSpin_Symbol` 放置、映射或写入 `Show_TP`，从而形成 `Show_State` 的过程。

Put 负责：

- 谁完成安置。
- 玩家能干预到什么程度。
- 抽取结果如何进入 Show_TP。
- 是否由玩家产生位置、顺序或选择关系。

Put 不负责：

- 从 Pool_Symbol 中随机抽什么。
- 安置完成后满足什么协同条件。
- 协同成立后的数值结算。

### 正式控制强度分类

Put 正式采用三类：

```text
自动
微手动
全手动
```

| 类型 | 正式解释 | 状态 |
|---|---|---|
| 自动 | 玩家不直接干预 Put，系统或装置完成全部安置 | 已确认 |
| 微手动 | 系统完成主要安置过程，玩家只能对局部步骤、有限选项或少量位置进行调整 | 已确认 |
| 全手动 | 玩家主动决定主要的选择、放置、映射或排列结果 | 已确认 |

对 Slot 母体而言，“自动”是父级基准；品类原型或游戏变体加入微手动、全手动控制时，应标记为对 Put 的**扩展**，而不是收窄。

旧版的 `auto_place / manual_set / manual_place / auto_set` 暂不进入新版正式枚举。

## 4.3 Combo

工作定义：

> Combo 是在 `Show_TP / Show_State` 上，依据 `C₁` 与 `C₂` 完成规则判定和结果结算的过程。

Combo 负责：

- 读取 Show_State 中的符号、数量、位置、顺序或关系。
- 判断是否满足协同规则。
- 在 C₁ 产生基础结果后，按需应用 C₂ 的修饰或结果转译。
- 输出 `Spin_Result`。

Combo 不负责：

- 从 Pool_Symbol 中抽取内容。
- 把抽取内容放入 Show_TP。
- 玩家在多次 Spin 之间进行的构筑调整。

### C₁：符号协同

> C₁ 是先验装置中的符号协同规则，其主要来源是玩家对该装置或现实原型已有的先验知识。

```text
C₁ = 符号协同
```

C₁ 的认知要求：

- 玩家几乎不需要重新学习。
- 或者只需要学习少量相对于既有先验的变化点。
- 协同规则应能从装置原型、符号关系或常识结构中被快速理解。

### C₂：二次揭晓

> C₂ 是作用于 C₁ 基础结果之上的可选二次规则层。C₁ 先建立本次结果的价值锚点，C₂ 再沿该结果逐步释放信息，揭晓它最终能够兑现到什么程度，并形成 `Spin_Result`。

```text
C₂ = 二次揭晓
```

C₂ 有两种一级实现方式：

- 修饰型：为 C₁ 基础结果增加倍率、条件、例外、连锁，或改变计算方式与性质，使其兑现程度逐步可见。
- 转译型：把 C₁ 基础结果映射为伤害、治疗、防御、技能触发、资源、状态或其他机制结果，并通过该过程逐步揭晓兑现程度。

C₂ 可以不启用：

- 当 C₁ 的基础结果能够直接成为 `Spin_Result` 时，Combo 不需要进入 C₂。
- 只有确定结果的播放只是结算动画，没有期待，不属于有效的 C₂。
- 推翻 C₁，或引入与 C₁ 无关的新随机，接近重新开奖，会削弱 C₁ 已经建立的价值。
- C₂ 可以保留不确定性，但这种不确定性必须来自 C₁ 结果的后续展开。

C₂ 与 C₁ 的核心区别：

```text
C₁ 识别先验装置中容易理解的符号协同，并产生基础结果
C₂ 在基础结果之后，选择性地二次揭晓 C₁ 的兑现程度
```

## 5. 双峰体验映射

## 5.1 第一峰

```text
第一峰 = Random + Put
```

体验内容：

- 对结果的不确定期待。
- 随机结果揭晓。
- 结果进入可见承载空间。
- 玩家在 Put 中进行有限或完整干预时产生的控制感。

第一峰的终点是：

```text
Show_State 已形成
```

## 5.2 第二峰

```text
第二峰 = Combo(C₁→C₂)
```

体验内容：

- 识别协同是否成立。
- 等待规则依次触发。
- 观察数值、动画或状态结算。
- 实际结果与预期之间的差异。

第二峰的终点是：

```text
Spin_Result 已形成
```

## 5.3 BD 的作用

BD 不属于单次 Spin 内的两个即时峰值，但它负责把多个 Spin 连接起来。

```text
多次 Spin
  →
观察结果
  →
BD
  →
改变后续 Pool / Random / Put / Combo 参数
  →
下一轮 Spin
```

BD 的具体可修改范围由机制母型、品类原型和游戏变体逐层约束。

原则上，BD 可以修改公式中的大部分可配置变量，包括：

- P(t) 中规则允许由玩家改变的目标、期限、容错或风险参数。
- Pool_Symbol 的内容、数量或权重。
- Random 的数量、概率或其他参数。
- Put 的控制方式和可操作范围。
- Show_TP 的参数，或在具体机制允许时改变其类型。
- C₁ 符号协同中的可变部分。
- C₂ 二次揭晓。
- N 和周期节奏。

BD 不改变体验模型的基本流程身份：

```text
Random → Put → Combo → BD
```

具体游戏允许修改其中哪些内容，由机制母型、品类原型和游戏变体继续限制。

## 6. 多次 Spin 与 BD 循环

### 6.1 周期结构

```text
Spin₁ → Spin₂ → … → Spinₙ → BD → 下一周期
```

### 6.2 工作形式化

设当前构筑状态为 `θₖ`：

```text
Spin_Resultᵢ = Spin(θₖ)

Progressₖ₊₁ = Evaluate(
  Spin_Resultᵢ,
  P(t)
)

θₖ₊₁ = BD(
  Spin_Result₁ … Spin_Resultₙ,
  θₖ
)
```

其中：

- `θ` 只是用于表达“当前构筑参数集合”的辅助符号。
- `P(t)` 是独立的目标压力上下文，不包含在 `θ` 中，也不使用 N 表达其检查周期。
- `θ` 暂不作为第一版网页中的一级术语。
- BD 可以改变哪些参数，由下层机制定义决定。

### 6.3 N 的正式定义

> 当下层启用 BD 时，`N` 表示触发一次 BD 之前连续发生的 Spin 数量。

规则：

- 当 BD 启用时，`N ≥ 1`。
- 多次 Spin 后触发一次 BD。
- N 的具体值由游戏规则动态决定，不要求是全局固定常数。
- 当每次 Spin 后都触发一次 BD 时，表示为 `N = 1`。
- 机制母型可以同时禁用 `N` 与 `BD`；此时只保留单次 Spin 核心流程。
- 品类原型可以在继承装置先验的基础上重新启用并扩展 `N → BD` 构筑循环。

当 BD 启用时，周期结构写为：

```text
[Spin]ₙ → BD，N ≥ 1（仅当 BD 启用）
```

## 7. 体验模型与下层原型的关系

体验模型不直接规定具体游戏机制：

```text
体验模型
  ↓ 被实现
机制母型
  ↓ 被约束与特化
品类原型
  ↓ 被继承与变异
游戏变体
```

每经过一层，都对同一组公式字段施加更多约束：

```text
P(t)
Pool_Symbol
Random
Put
Show_TP
C₁
C₂
N
BD
```

Slot 母体当前先建立四个品类原型。四类来自两个互相独立的分析维度：

- 继承方式：保留 Slot 核心后扩展（`Slot+`）／保留装置认知但改写 Pool_Symbol 或 C₁（`Slot改`）。
- 结果模式：战斗表现／数值表现。

```text
双峰多巴胺
  →
Slot母体
  ├── Slot+战斗型（基石游戏：Slotbound）
  ├── Slot+数值型（基石游戏：四叶草深渊）
  ├── Slot改·战斗型（基石游戏：魔王终局）
  └── Slot改·数值型（基石游戏：幸运房东）
        └── 幸运市长
```

其中 `C₂` 负责沿 C₁ 基础结果二次揭晓其最终兑现程度，形成战斗或数值型 `Spin_Result`；`P(t)` 负责判断该结果对于当前战斗／数值目标是否足够。

## 8. 与旧版 v5 的关系

新版内容与旧版代码、数据完全解耦。

| 项目 | 旧版 v5 | 202607 新版 |
|---|---|---|
| Random 作用域 | 基础池随机抽取，默认输出多重集 | 明确 `Random@Pool_Symbol` |
| Random 输出 | 多重集 | `SingleSpin_Symbol`，不强制为无序多重集 |
| Put 分类 | 自动/手动 × set/place 四类 | 自动/微手动/全手动三类 |
| 承载空间 | `show_topology` | `Show_TP` |
| 空间实例 | 未单独命名 | 新增 `Show_State` |
| 决策阶段 | `RPBD` | `BD` |
| 公式重点 | 游戏拆解与评分 | 体验模型与逐层约束 |

旧版的以下内容在新版中的处理状态：

- 五种 Show Topology 已重新确认为新版 Show_TP 五类。
- 四种 Put Form。
- 八种 Combo Predicate。
- 基础池／主动池划分。
- 压力参数迁移到 P(t) 的待确认观察，不再机械写入 N。

除 Show_TP 五类外，其余旧版项目仍需在新版中重新确认后才视为冻结内容。
