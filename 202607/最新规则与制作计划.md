# 一、本次范围决策

## 1.1 架构目标

系统最终要支持：

- 多个机制母型横向并列。
- 每个机制母型下有多个品类原型。
- 每个品类原型下有多个品类变体。
- 每个层级都能挂接具体产品、案例和证据。
- 所有机制母型、品类原型、品类变体都必须映射到体验模型公式。

## 1.2 首版内容范围

首版只制作一条完整链：

```text
体验模型：双峰多巴胺
    ↓
机制母型：Slot
    ↓
品类原型：Slot 数值型（暂定名）
    └── 代表产品：《幸运房东》
            ↓
品类变体：《幸运城市》
```

说明：

- “Slot 数值型”是当前暂定的**品类原型名称**。
- 《幸运房东》是该品类原型的来源与代表产品。
- 《幸运城市》是该品类原型下首个需要分析的品类变体。
- “Slot 战斗型—《魔王终局》”只作为未来扩展示例，本次不录入正式内容。
- Dice、Roulette、Pachinko 等其他机制母型本次不录入正式内容。
- 页面和数据结构必须支持未来扩展，但首版页面不能用虚构节点填充数量。

## 1.3 首版真实数量

首版正式数据应显示：

```text
机制母型：1
Slot 下的品类原型：1
Slot 数值型下的品类变体：1
```

所有数量必须从数据自动计算，禁止直接写死在页面里。

# 二、统一术语与层级规则

## 2.1 固定术语

统一使用：

1. **体验模型**
2. **机制母型**
3. **品类原型**
4. **品类变体**
5. **具体产品**

不再使用“机制母体”。

## 2.2 每个层级的职责

| 层级 | 作用 | 本次实例 |
|---|---|---|
| 体验模型 | 定义体验的抽象动力结构 | 双峰多巴胺 |
| 机制母型 | 基于装置先验，对体验公式施加第一层约束 | Slot |
| 品类原型 | 在机制母型基础上形成可识别、可复用的玩法范式 | Slot 数值型 |
| 品类变体 | 继承品类原型并改变部分公式内容 | 幸运城市 |
| 具体产品 | 提供原型或变体的现实证据与完整实例 | 幸运房东、幸运城市 |

## 2.3 产品与原型必须分开

《幸运房东》既是具体产品，也是“Slot 数值型”品类原型的主要提炼来源，但数据中必须分成两个对象：

```text
品类原型：Slot 数值型
代表产品：幸运房东
```

这样以后可以在同一品类原型下增加其他产品，而不需要改变原型本身。

品类原型页面可以显示：

```text
Slot 数值型
代表原型产品：《幸运房东》
其他归属产品：未来添加
```

# 三、公式中心规则

## 3.1 最新核心公式

```text
[
  Random @ Pool_Symbol
    →
  Put @ Show_TP
    →
  Combo(C₁ → C₂?) @ Show_TP
]ₙ
  →
BD
```

## 3.2 数据流

```text
Pool_Symbol
  ──Random──>
SingleSpin_Symbol
  ──Put @ Show_TP──>
Show_State
  ──Combo(C₁→C₂?) @ Show_TP──>
Spin_Result
```

## 3.3 强制映射规则

每一个机制母型、品类原型和品类变体都必须提供“公式指纹”，至少覆盖：

- `Pool_Symbol`
- `Random`
- `Put`
- `Show_TP`
- `Combo₁`
- `Combo₂`
- `N`
- `BD`

每条正式分析必须回答：

1. 它位于公式的哪个字段？
2. 它继承了父级什么？
3. 它对父级进行了什么约束或变化？
4. 它改变了第一峰、第二峰还是 BD 循环？

无法映射到公式的内容：

- 可以作为题材、美术、商业或补充说明存在；
- 不得被写成机制母型、品类原型或品类变体的核心定义。

## 3.4 约束操作

节点对公式字段只能使用以下正式操作：

| 操作 | 含义 |
|---|---|
| `inherit` | 完全继承父级 |
| `default` | 给出先验默认值，下级仍可修改 |
| `restrict` | 收窄允许范围 |
| `fix` | 固定为具体值 |
| `override` | 替换父级定义 |
| `extend` | 保留父级并增加新能力 |
| `compose` | 组合另一个机制母型的部分先验 |

首版虽然只制作单条继承链，数据结构仍保留 `compose` 能力。

# 四、三级横向浏览规则

第二部分的核心不是一张无限展开的大图，而是一个**三级横向浏览器**。

## 4.1 第一级：机制母型横向总览

用户进入“原型图谱”后，首先看到全部机制母型。

页面顶部必须显示：

```text
机制母型共 X 种
```

每张机制母型卡片至少显示：

- 母型名称。
- 一句话定义。
- 公式指纹摘要。
- 品类原型数量。
- 品类变体总数量。
- 具体产品总数量。
- 是否存在待完善内容。

首版实际状态：

```text
机制母型共 1 种

[ Slot ]
品类原型 1
品类变体 1
具体产品 2
```

以后增加其他机制母型时，自动横向增加卡片。

### 交互规则

- 卡片横向排列。
- 数量较多时可以横向滚动。
- 当前选中的母型高亮。
- 支持按名称搜索。
- 支持“只看已完成 / 包含草稿”筛选。
- 点击母型进入第二级，但第一级仍保留在页面上方。

## 4.2 第二级：所选母型下的品类原型

选中 Slot 后，页面显示：

```text
Slot
包含 X 种品类原型
```

每张品类原型卡片至少显示：

- 品类原型名称。
- 所属机制母型。
- 代表产品。
- 核心公式差异摘要。
- 品类变体数量。
- 归属产品数量。

首版实际状态：

```text
Slot
包含 1 种品类原型

[ Slot 数值型（暂定名） ]
代表产品：幸运房东
品类变体：1
```

未来可扩展为：

```text
Slot
├── Slot 数值型
│   └── 代表产品：幸运房东
└── Slot 战斗型
    └── 代表产品：魔王终局
```

但首版不能把“Slot 战斗型”或《魔王终局》写入正式页面数据。

### 交互规则

- 原型卡片横向排列。
- 点击原型后进入第三级。
- 保留当前 Slot 母型选中状态。
- 显示路径：

```text
机制母型 / Slot / Slot 数值型
```

## 4.3 第三级：所选品类原型下的品类变体

选中“Slot 数值型”后，页面显示：

```text
Slot 数值型
包含 X 种品类变体
```

每张品类变体卡片至少显示：

- 变体名称。
- 父级品类原型。
- 继承项数量。
- 覆写项数量。
- 扩展项数量。
- 代表/对应产品。
- 一句话变化摘要。

首版实际状态：

```text
Slot 数值型
包含 1 种品类变体

[ 幸运城市 ]
继承自：Slot 数值型
```

### 交互规则

- 变体卡片横向排列。
- 点击变体后打开详情。
- 保留上方选中的 Slot 与 Slot 数值型。
- 显示完整路径：

```text
机制母型 / Slot / Slot 数值型 / 幸运城市
```

## 4.4 详情区

在任一级选中节点后，详情区都必须显示：

1. 节点定义。
2. 父级关系。
3. 子节点数量。
4. 对应具体产品。
5. 公式指纹。
6. 相对父级的变化。
7. 变化影响的体验位置。
8. 证据和说明。

详情区不应替代三级横向浏览；两者同时存在：

```text
横向浏览：回答“有多少、有哪些”
详情区域：回答“它是什么、改变了什么”
```

## 4.5 大量节点时的规则

未来节点增多后：

- 第一级只横向展示机制母型卡片。
- 第二级只展示当前母型的直接品类原型。
- 第三级只展示当前原型的直接品类变体。
- 不在同一画布上一次性展开所有后代。
- 支持搜索结果直接定位并自动选中祖先路径。
- 卡片数量显示真实直接子级数量。
- 母型卡片额外显示所有后代的汇总数量。

这样既能横向比较，也不会因为节点增多而失去可读性。

## 5.3 品类原型

每个品类原型至少包含：

```text
id
name
name_status
primary_mother_id
composed_mother_ids
representative_product_ids
formula_changes
identity_rules
variant_ids
status
order
```

`name_status` 用于标记“Slot 数值型”仍是暂定名。

## 5.4 品类变体

每个品类变体至少包含：

```text
id
name
prototype_id
product_ids
formula_changes
inheritance_summary
status
order
```

## 5.5 具体产品

每个具体产品至少包含：

```text
id
name
relation_type
mother_ids
prototype_ids
variant_ids
evidence
status
```

产品关系可以是：

- `source`：原型提炼来源。
- `representative`：代表产品。
- `member`：归属产品。
- `variant_instance`：品类变体的具体实例。

## 5.6 数量计算

页面中的数量必须通过关系自动计算：

```text
母型的品类原型数
= primary_mother_id 指向该母型的原型数量

母型的品类变体总数
= 该母型所有品类原型下的变体数量

原型的品类变体数
= prototype_id 指向该原型的变体数量

产品数量
= 与节点建立正式关系的去重产品数量
```

禁止在数据中手工维护：

```text
prototype_count
variant_count
product_count
```

否则新增内容后容易产生数量不同步。

## 5.7 新增内容工作流

以后用户提出“添加新的机制母型或产品”时，按以下顺序处理：

1. 判断新增对象是机制母型、品类原型、品类变体还是具体产品。
2. 确定父级关系。
3. 映射到公式字段。
4. 写出相对父级的变化。
5. 建立产品证据关系。
6. 写入对应数据文件。
7. 运行关系、循环和字段校验。
8. 页面自动更新数量和横向卡片。
9. 检查详情页与公式跳转。

正常新增内容不允许修改核心页面布局代码。
